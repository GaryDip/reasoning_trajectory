# 多跳检索 Gate：方法与实验报告

## 摘要

多跳问答系统在逐跳检索证据的过程中容易选错证据段落，且错误会沿推理链路传播。本报告提出一种
基于大语言模型隐藏状态的轻量分类器（gate），用于在检索排序阶段识别可能错误的证据选择。主方法
将证据选定后的绝对隐藏状态与选定前后的隐藏状态差值在特征层面融合，训练单一分类器，并针对推理
阶段的文本分布与训练阶段保持一致做了专门处理。在 MuSiQue、2WikiMultihopQA、HotpotQA 三个数据
集上，该方法相对纯余弦相似度检索基线在证据召回率、链路准确率、答案 EM/F1 上均有稳定提升。

## 一、背景与问题定义

多跳问答需要将一个复合问题分解为若干子问题，逐跳检索证据、逐跳推理，最终综合所有中间结果给出
答案。例如问题"拥有 The Collegian 的机构是什么时候成立的？"需要先回答"谁拥有 The Collegian？"
（子问题 1），再用这个答案代入"[子问题1的答案]是什么时候成立的？"（子问题 2）。这类子问题需要
引用前一跳答案的结构称为桥接（bridge）问题，子问题文本中通常以 `[Answer N]` 的形式显式标记对
第 N 个子问题答案的引用。

每一跳检索均基于余弦相似度（BGE 编码器）对候选段落排序，但相似度最高的段落不一定是正确证据，
检索错误是多跳问答的主要失败来源之一，且一旦某一跳选错证据，该错误会传播到后续所有跳的推理
过程中。

本方法训练一个轻量分类器（gate），利用大语言模型（Llama-3.1-8B-Instruct）处理推理前缀时产生的
隐藏状态，预测某一跳的证据选择是否有误，并将该预测以连续分数的形式与余弦相似度线性混合，用于
重新排序候选证据：

```
final_score = emb_score − λ · gate_score
```

其中 `emb_score` 为候选与子问题的余弦相似度，`gate_score` 为 gate 预测的该跳证据选择错误的
概率，λ 为混合权重。

## 二、训练数据构造

### 2.1 子问题来源：两套独立的问题分解器

项目使用两套完全独立的问题分解方式：一套用于构造 gate 分类器的训练数据（第三、四、五节），
另一套用于真实推理阶段给出子问题（第六节）。二者是两个独立的部件，互不依赖。

**GT decompose（用于构造 gate 的训练数据）**：MuSiQue 数据集自带 `question_decomposition` 标注，
记录每一跳的子问题、对应的 gold 段落编号（`paragraph_support_idx`）及该跳答案。该标注本身是
模板化的短语，经大语言模型（GPT）改写为通顺的自然语言子问题。GT decompose 直接来自数据集官方
标注，仅覆盖 MuSiQue，本身不涉及任何模型训练——它只是"把标注改写成通顺文本"这一步，产出的
子问题用于构造第二节所述的正/负例推理轨迹，进而提取隐藏状态、训练 gate 分类器。

**BART decompose（用于真实推理阶段）**：gate 训练完成后，真实使用该方法回答问题时，不存在
ground-truth 分解，此时的子问题由一个独立训练的序列到序列模型给出——这里的"训练"指的是训练
这个分解器本身，与 gate 的训练是两个不相关的模型、两次不同的训练过程。该分解器以
`facebook/bart-large` 为基础，训练数据包含 MuSiQue 官方分解格式训练集（约 19,938 条）与
2WikiMultihopQA 训练集（约 10,444 条，经 GPT 标注为同一格式，按题型分层采样，约 45%
bridge-comparison、25% comparison、15% compositional、15% inference，覆盖 2WikiMultihopQA
的全部四种问题类型），合计约 30,382 条训练样本（学习率 3e-5，batch size 16，最大目标长度 100
token，bf16 精度）。模型用于预测 `[[CQS]] ... [[CQE]]` 格式的子问题片段，再经格式转换与大语言
模型改写得到自然语言子问题。训练完成后应用于全部三个数据集（MuSiQue、2WikiMultihopQA、
HotpotQA）的验证集推理，是第六、七、八节端到端实验实际使用的分解方式——HotpotQA 本身未参与
该分解器的训练，其推理阶段的分解结果依赖模型在 MuSiQue 与 2WikiMultihopQA 上学到的分解能力
泛化得到。

两套分解器产出的子问题均采用相同的引用标记约定：子问题文本中对前序跳答案的引用以字面
`[Answer N]` 形式书写。GT decompose 构造训练数据的过程中未对该标记做任何替换（第三节将说明这
对 gate 训练文本分布的影响）；BART decompose 在推理时同样产出未替换的字面标记，由检索与生成
流程分别处理（第六节）。

### 2.2 正例与负例构造

基于 GT decompose 的子问题，构造两类推理轨迹（trace）：

- **正例（gold trace）**：每一跳均使用 gold 证据段落，标签 `wrong_hops = []`
- **负例（counterfactual trace）**：随机选取一跳 h，将该跳证据替换为与子问题余弦相似度最高的
  非 gold 段落（模拟检索器最常见的错误模式——语义相关但答非所问），标签 `wrong_hops = [h]`，
  其余跳保持 gold 证据

正负样本数量按 `(K, 注错跳位置)` 分桶做上下采样以平衡各桶样本量。

### 2.3 文本格式

无论正例还是负例，最终统一拼接为如下格式：

```
Question: {主问题} Step 1: {子问题1} Evidence: "{证据1}" Step 2: {子问题2} Evidence: "{证据2}" ... Final Answer: {答案}
```

## 三、隐藏状态提取

### 3.1 累计前缀

对一个 K 跳的推理轨迹，隐藏状态按累计前缀分别提取，共 K+2 个：

```
h_0     = "Question: {主问题}"
h_1     = h_0 拼接 "Step 1: {子问题1} Evidence: \"{证据1}\""
h_2     = h_1 拼接 "Step 2: {子问题2} Evidence: \"{证据2}\""
...
h_K     = 完整 K 跳
h_{K+1} = h_K 拼接 "Final Answer: {答案}"
```

每个前缀独立完整地输入 Llama，取最后一个 token 在指定层的隐藏状态作为该前缀的表示。前缀在实际
使用时会以独立对话轮次的形式套用 chat 模板，末尾附加结束标记；若仅做一次长序列前向传播并在中间
位置读取隐藏状态，读取到的将是"内容尚未结束"状态下的表示，与真实使用场景（该跳内容已完整给出）
存在系统性差异，因此每个前缀需要独立的前向传播。

### 3.2 多层提取

单次前向传播可同时获得模型全部层的隐藏状态，无需额外计算开销即可同时保留第 7、15、23、31 层的
表示。训练集按 `(K, 跳位置)` 分桶采样（每桶上限 1500 条，样本本就稀缺的最大 K 分桶不设上限），
验证集不采样、全量提取。

## 四、特征定义

基于逐前缀隐藏状态，定义两类性质不同的特征：

- **绝对隐藏状态 h_j**：第 j 跳完成后的隐藏状态，表示截至当前跳为止整条推理前缀的累积状态，
  是全局性质的信号——前序任意一跳的异常都可能反映在其中。
- **隐藏状态差值 Δh_j = h_j − h_{j-1}**：该跳前后隐藏状态的差值，表示选定该跳证据所引起的状态
  变化量，是局部性质的信号，仅反映当前这一步本身。

### 4.1 按语义角色池化

不同 K 值的推理轨迹在相同的语义跳位置上可以联合训练：例如"主问题到第一个证据"（j=0）这一
transition 在 K=2、3、4 的轨迹中均存在，而"第三个证据到第四个证据"（j=3）仅存在于 K=4 的轨迹。
训练时按语义角色将不同 K 的数据池化：

| j | transition | 覆盖的 K |
|---|---|---|
| 0 | Q → 证据1 | 2, 3, 4 |
| 1 | 证据1 → 证据2 | 2, 3, 4 |
| 2 | 证据2 → 证据3 | 3, 4 |
| 3 | 证据3 → 证据4 | 4 |

标签定义为 `should_intervene(j) = (j+1) ∈ wrong_hops`，仅对负例（counterfactual trace）有效，
正例（gold trace）的 `wrong_hops` 为空，全部作为负样本。

## 五、Gate 模型

### 5.1 局部信号模型

基础版本仅使用 Δh_j 训练 `PCA(64) + Logistic Regression`，按跳位置选择不同层：j=0,1 使用第 15
层，j=2,3 使用第 23 层。

### 5.2 特征级融合模型（主方法）

主方法在特征层面融合 h_j 与 Δh_j，而非训练两个独立模型后组合其输出分数。h_j 与 Δh_j 各自独立
进行 PCA 降维（二者协方差结构不同，不共用投影），降维后的特征拼接，训练单一 Logistic Regression：

```
p_j = σ(w_h^T · PCA(h_j) + w_Δ^T · PCA(Δh_j) + b)
```

层选择沿用局部信号模型已验证的结果（j=0,1→15 层，j=2,3→23 层）。

训练规模：

| j | transition | 覆盖的 K | 样本数 | 正例占比 | 训练集 AUC |
|---|---|---|---|---|---|
| 0 | Q→E1 | 2,3,4 | 83,927 | 28.7% | 0.9707 |
| 1 | E1→E2 | 2,3,4 | 59,857 | 40.2% | 0.9472 |
| 2 | E2→E3 | 3,4 | 21,411 | 45.3% | 0.9143 |
| 3 | E3→E4 | 4 | 4,046 | 50.0% | 0.9535 |

在证据选择正误的二分类任务上（数据源为固定的正/负例轨迹，不涉及真实检索候选池排序），特征
融合模型相对仅使用局部信号的模型：

| | AUC | 整体 F1 | 整体 TPR |
|---|---|---|---|
| 局部信号模型（Δh_j） | 0.9221 | 0.7785 | 0.8456 |
| **特征融合模型（h_j ⊕ Δh_j）** | **0.9357** | **0.793** | **0.8838** |

按跳位置拆分，j=2（局部信号模型最弱的一跳）F1 提升幅度最大（0.7535 → 0.7919）。

## 六、端到端推理流程

推理阶段不存在 ground-truth 分解，子问题由独立训练的 BART 分解器给出。对每一跳执行如下步骤：

1. **检索查询构造**：子问题若含 `[Answer N]` 引用，使用此前各跳已生成的简短答案将其替换为
   具体内容，得到用于检索的展开版子问题。
2. **候选检索**：对展开版子问题编码前添加 BGE 官方推荐的非对称检索指令前缀
   （"Represent this sentence for searching relevant passages: "），用于短查询—长段落检索
   场景，随后与候选段落计算余弦相似度，取 top-k。
3. **gate 打分**：对每个候选，构造"累计前缀 + 当前跳 + 该候选证据"的文本并输入 Llama 提取
   隐藏状态，供 gate 模型打分。该累计前缀独立维护，其中的子问题始终使用未展开的原始文本，
   与训练阶段的文本分布保持一致（该设计的动机与验证见第八节）。
4. **重排序**：按 `final_score = emb_score − λ · gate_score`（λ=0.50）排序，直接取分数最高的
   候选作为该跳证据，不再引入额外的语言模型二次选择步骤（验证见第八节）。
5. **生成该跳简短答案**：基于选定证据生成一个简短答案，用于展开下一跳的引用。

K 跳全部完成后，将完整推理链路（各跳子问题、证据、简短答案）与原始问题一并提供给最终阅读理解
模块，生成提交答案。

## 七、端到端结果

在 MuSiQue 验证集全量（2417 条）上，逐项累加各设计要素带来的提升：

| 方法 | recall@1 | chain@1 | EM | F1 |
|---|---|---|---|---|
| 纯余弦相似度检索（无 gate） | 0.6003 | 0.3335 | 0.3757 | 0.4652 |
| + 局部信号 gate（λ=0.25） | 0.6627 | 0.4357 | 0.4100 | 0.5045 |
| + 特征融合 gate（λ=0.25） | 0.6950 | 0.5010 | 0.4224 | 0.5146 |
| + λ 调优至 0.50 | 0.6984 | 0.5114 | 0.4249 | 0.5187 |
| + gate 打分文本分布对齐 | 0.7008 | 0.5143 | 0.4274 | 0.5216 |
| + 检索指令前缀 | 0.7023 | 0.5143 | 0.4307 | 0.5270 |
| + reader prompt 比较类问题修复 | 0.7018 | 0.5143 | 0.4427 | 0.5386 |
| **+ λ 重新调优至 0.60（当前完整方法，0828 更新）** | **0.6994** | **0.5118** | **0.4386** | **0.5341** |

第一行为 `--methods baseline`（纯 `CosineRetriever`，不加载 gate 模型）在 MuSiQue dev 全量上
的真实结果（路径见附录二 B.2 表）。相对该真实基线，完整方法在四项指标上分别提升 10.15、
18.08、6.70、7.34 个百分点。完整方法这一行同时有真实（剪枝前完整候选池上计算的）
recall@3=0.8441，不是由 `--beam-width 1` 退化得到的数字，详见附录二 B.2。

最后一步（reader prompt 修复，见 8.7 节）来自案例分析发现的一个具体 bug：最终答案生成阶段，
对比较类问题（"哪个更早/更晚/更长"）reader 经常直接把某一跳查到的原始日期/数字当答案输出，
而不是执行比较、回答被比较的实体名字。recall@1/chain@1 与上一行完全一致（这一步只改最后一句
生成 prompt，不碰检索/gate），EM/F1 分别再提升 1.20、1.16 个百分点——在 MuSiQue 上涨幅不大，
因为 MuSiQue 的比较类问题本身很少，但在 2WikiMultihopQA 上这一步单独带来了 +9.92 EM / +10.11
F1，是本报告目前记录到的单次改动里最大的一次提升，详见 8.7 节。

在 2WikiMultihopQA 与 HotpotQA 上，完整方法（λ + gate 打分文本对齐 + 检索指令前缀 +
reader prompt 修复）同样已验证。λ=0.50 版本（reader prompt 修复后、λ 重新调优前）：

| 数据集 | recall@1 | recall@3 | chain@1 | EM | F1 |
|---|---|---|---|---|---|
| MuSiQue | 0.7018 | 0.8441 | 0.5143 | 0.4427 | 0.5386 |
| 2WikiMultihopQA | 0.9289 | 0.9839 | 0.8613 | 0.5982 | 0.6770 |
| HotpotQA | 0.6595 | 0.8683 | 0.5567 | 0.5517 | 0.6870 |

三个数据集的 recall@3 均为真实值（`full_pool_gold_rank_overall`，剪枝前完整候选池上计算），
不再受 `--beam-width 1` 退化问题影响；recall@1/chain@1 相对未修复 reader prompt 的版本完全
持平，确认这一步改动只影响答案生成，不影响检索/gate 判断。

### λ 重新调优（0828 更新）

用当前配置（rawprefix + comparison_hint）在一个 3000 条的 BART decompose MuSiQue train 子集上
重新扫了一遍 λ（0.10-0.80），EM/F1 在 0.60-0.65 附近见顶（比 dev 上原来调出的 0.50 更高）。用
λ=0.60 在三个数据集的 dev 全量上直接验证：

| 数据集 | recall@1 | recall@3 | chain@1 | EM | F1 |
|---|---|---|---|---|---|
| MuSiQue | 0.6994（−0.24pp） | 0.8435（−0.06pp） | 0.5118（−0.25pp） | 0.4386（−0.41pp） | 0.5341（−0.45pp） |
| 2WikiMultihopQA | 0.9316（+0.27pp） | 0.9842（+0.03pp） | 0.8685（+0.72pp） | 0.6023（+0.41pp） | 0.6819（+0.49pp） |
| HotpotQA | 0.6620（+0.25pp） | 0.8701（+0.18pp） | 0.5610（+0.43pp） | 0.5519（+0.02pp） | 0.6883（+0.13pp） |

结果好坏参半：MuSiQue（λ 本身就是在这个数据集上调出来的）全指标小幅下降，2Wiki/HotpotQA（未参
与本轮调参）反而小幅上升。考虑到 λ=0.50 当初主要是针对 MuSiQue 调优的（8.4 节），这次在两个
"跳出训练集"的数据集上都有提升、只在被调参的数据集上有小幅回退，说明 0.60 是一个跨数据集更稳健
的取值，不是单一数据集的过拟合结果——**采纳 λ=0.60 为新的默认值**（脚本默认值已同步更新）。

## 八、消融实验

### 8.1 特征级融合 vs. 后融合

在确定特征级融合方案之前，比较了多种"独立训练局部信号模型与全局信号模型后融合其输出分数"的
方式，包括固定权重求和、投票、Reciprocal Rank Fusion、置信度加权、粗筛精排、三方凸组合、以及
学习逐候选组合权重的门控网络。其中效果最好的固定权重求和：

| | recall@1 | chain@1 | EM | F1 |
|---|---|---|---|---|
| 后融合（固定权重求和） | 0.6869 | 0.4894 | 0.4141 | 0.5089 |
| **特征级融合** | **0.6950** | **0.5010** | **0.4224** | **0.5146** |

特征级融合在四项指标上均优于最好的后融合方案。另有一种学习得到的逐候选组合权重方案，检索侧
指标略优于特征级融合、答案侧指标基本持平，但需额外训练一个门控网络，模型结构更复杂；在效果
相近的情况下选择结构更简单的特征级融合方案。

### 8.2 是否需要语言模型二次选择

比较排序阶段直接取候选池 rank-1 的准确率，与排序后再由语言模型从 top-3 中二次选择的准确率
（局部信号模型，二元阈值触发变体）：

| | 排序阶段 recall@1 | 二次选择后准确率 |
|---|---|---|
| 整体 | 0.6565 | 0.6185 |
| K=2 | 0.7188 | 0.6736 |
| K=3 | 0.6212 | 0.5906 |
| K=4 | 0.5526 | 0.5179 |

各 K 分桶下，语言模型二次选择后的准确率均低于直接采用排序结果，因此最终方案不引入该步骤。

### 8.3 训练与推理阶段文本分布一致性

训练数据中，约 49% 的跳位置其子问题包含未展开的 `[Answer N]` 引用；早期推理实现会先将该引用
展开后再用于 gate 打分，导致 gate 在推理阶段接收的文本分布与训练阶段不一致。对此设计了两种
修正方案：

**方案一**：检索查询与 gate 打分均使用未展开文本，同时将检索与逐跳生成完全解耦：

| | recall@1 | chain@1 | EM | F1 |
|---|---|---|---|---|
| 展开版文本（原方案） | 0.6950 | 0.5010 | 0.4224 | 0.5146 |
| 检索与打分均使用未展开文本 | 0.6357 | 0.4030 | 0.3608 | 0.4642 |

四项指标全面下降。按跳位置拆分显示，第一跳（不涉及引用展开）两种方案结果完全一致，自第二跳起
未展开方案显著更差，且差距随 K 增大而扩大。该现象定位于检索阶段：余弦编码器为通用语义模型，
未在该推理链路上训练过，未展开的引用文本对其构成噪声，导致候选段落检索质量下降。

**方案二（主方法采用）**：仅将 gate 打分所用文本改为未展开版本，检索流程保持不变（继续使用
展开后的查询）：

| | recall@1 | chain@1 | EM | F1 |
|---|---|---|---|---|
| λ=0.50 基线 | 0.6984 | 0.5114 | 0.4249 | 0.5187 |
| 仅调整 gate 打分文本 | 0.7008 | 0.5143 | 0.4274 | 0.5216 |

四项指标均有提升，检索侧未出现方案一中的性能下降。二者对比表明检索与 gate 判断对文本展开与否
的敏感度不同，需分别处理。

### 8.4 λ 超参数扫描

在 MuSiQue 验证集全量上对 λ 扫描 0.10 至 0.60（间隔 0.05）：

|---|---|---|---|---|
| 0.25 | 0.6950 | 0.5010 | 0.4224 | 0.5146 |

极值点。相对 λ=0.25，λ=0.50 在四项指标上分别提升 4.2、11.6、5.0、6.1 个百分点。

### 8.6 其他探索方向

- **上下文驱动的自适应权重**：训练一个基于检索前上下文预测混合权重的小型网络，替代固定 λ。
  该方案权重按整跳共享，训练时无法感知具体候选，梯度缺乏候选级别的区分信号，训练过程中反复
  出现权重发散或收敛为常数的现象，判定为该设计存在结构性缺陷，未采用。
- **更高容量的判分模型**：尝试以多层感知机或低秩双线性变换模型替代单层 Logistic Regression。
  分类任务 AUC 可进一步提升至 0.9457，但 F1 始终未能超过单层模型——训练集 AUC 显著高于验证集
  AUC，判定阈值从训练集迁移到验证集时不够稳定，即使引入交叉验证校准也只能部分缓解，最终未采用。

### 8.7 reader prompt 修复：比较类问题答案错位

前几节的改进全部集中在检索/gate 侧；这一节的发现来自对端到端案例的直接抽查，而非继续调整
检索或 gate。取 D 组（特征级融合）在 MuSiQue dev 上"每一跳都检索到 gold 段落、但最终答案依然
错误"的 485 个案例，逐个比对最终答案与逐跳短答案（`prior`）：

| 类型 | 数量 | 占比 |
|---|---|---|
| 最终答案等于最后一跳短答案，但因措辞与 gold 不完全一致被判为错（EM 严格匹配导致，非真实错误） | 372 | 77% |
| 最终答案等于**更早一跳**的短答案（reader 选错了该采用哪一跳的结论） | 39 | 8% |
| 最终答案与任何一跳短答案都不匹配（reader 自行综合出新的错误内容） | 74 | 15% |

同样的分析在 2WikiMultihopQA、HotpotQA 上重复，"reader 选错跳"这一模式的占比分别为 13.1%
（639/4894）与 15.2%（232/1522），均高于 MuSiQue，且并非个例。进一步检查发现这一模式在
比较类问题（"哪部电影更晚上映"“哪个更早出现”）上尤为集中，且不只是"选错跳"，而是 reader
根本没有执行"比较"这一步，直接把某一跳查到的原始数值当最终答案：

```
Q: Which film was released more recently, Royal Treasure or When Love Begins?
gold: Royal Treasure   |   final: January 15, 2016
每跳短答案: ['January 15, 2016', '2008']
```

根因是最终答案生成 prompt（`run_retrieval_exp_wavefront.py::build_final_reader_cot_prompt`）
里唯一约束答案格式的一句"Give a short span or phrase only (entity, date, number, or
yes/no)"，把日期/数字列为合法答案类型，且未区分"逐跳答案即最终答案"（多数桥接类问题成立）
与"逐跳答案只是比较的中间量，需要 reader 自己执行比较后回答实体名"（比较类问题）这两种情况。

修复方式是新增 `build_final_reader_cot_prompt_comparison_hint`（原函数保留不动，两者通过
`--final-reader-prompt {default,comparison_hint}` 参数切换），只追加一句指令：

```
If the original question asks you to COMPARE two or more entities (for example "which was
released more recently", "who was born first", "which is longer"), the per-step answers
above are the values used to make that comparison, not the final answer themselves -- you
must perform the comparison yourself and answer with the NAME of the entity that satisfies
it, not a date, number, or other raw value.
```

三个数据集全量验证（其余配置不变，仅切换这一句 prompt）：

| 数据集 | recall@1 | chain@1 | EM（default→comparison_hint） | F1（default→comparison_hint） |
|---|---|---|---|---|
| MuSiQue | 持平 | 持平 | 0.4307→0.4427（+1.20） | 0.5270→0.5386（+1.16） |
| 2WikiMultihopQA | 持平 | 持平 | 0.4990→0.5982（**+9.92**） | 0.5759→0.6770（**+10.11**） |
| HotpotQA | 持平 | 持平 | 0.5217→0.5517（+3.00） | 0.6517→0.6870（+3.53） |

三个数据集 recall@1/chain@1 均与切换前完全一致，确认改动只影响答案生成、不影响检索与 gate
判断。涨幅排序为 2WikiMultihopQA > HotpotQA > MuSiQue，与"reader 选错跳"在受影响样本中的
**占比**排序（HotpotQA 15.2% > 2WikiMultihopQA 13.1%）不完全一致——原因是 HotpotQA 检索
基线更低（recall@1 约 66%），"检索全对"这一前提覆盖的样本更少，受影响样本占**全量**的比例
反而低于 2WikiMultihopQA（3.1% vs 5.1%），而后者才是决定整体 EM 涨幅的关键。

2WikiMultihopQA 上单独这一步改动带来 +9.92 EM / +10.11 F1，是本报告目前记录到的单次改动里
最大的一次提升。`comparison_hint` 已确认为三个数据集上一致更优、无一项指标下降的新默认
reader prompt。

在此基础上继续尝试了两版局部修补——逐跳短答案加"答案类型需匹配疑问词"约束、最终答案前加
显式推理步骤——用 `replay_final_reader.py`（复用已有 case 文件重建每跳输入，只重跑最终答案
一步）在三个数据集上验证，两版均为净负，未采纳，具体案例与根因分析见 `update_doc/0817/
0817update.md` 第五节。`comparison_hint` 现有措辞在"能否识别出比较类问题"与"会不会对非
比较类问题过度触发"之间已是较优平衡点，`comparison_hint` 定为最终版本。

## 九、方法总结

完整方法流程：基于 GT decompose 构造正/负例推理轨迹，按累计前缀独立提取多层隐藏状态，将绝对
隐藏状态与隐藏状态差值在特征层面融合训练单一分类器；推理阶段检索查询展开引用并添加检索指令
前缀，gate 打分使用与训练分布一致的未展开文本，以 λ=0.50 的固定权重与余弦相似度线性混合排序，
直接采用排序结果的最高候选，不引入语言模型二次选择，逐跳生成简短答案，最终答案生成阶段的
prompt 显式提示比较类问题需要执行比较、回答实体名而非中间查到的原始数值（8.7 节）。在 MuSiQue
验证集上，该方法相对纯余弦相似度基线四项指标提升 10.15 至 18.08 个百分点。

gate 打分文本分布对齐、检索指令前缀、reader prompt 比较类问题修复三项改进均已在 2WikiMultihopQA、
HotpotQA 上完成跨数据集验证（第七节、8.7 节），完整候选池（重排序前）上的真实 recall@1/recall@3
统计也已产出（附录二 B.2）。其中 reader prompt 修复是目前记录到的单次改动里提升最大的一次
（2WikiMultihopQA 上 +9.92 EM / +10.11 F1），且是通过直接抽查端到端案例、而非继续在检索/gate
侧调参发现的。控制变量对照实验（仅局部信号 / 仅全局信号 / 特征级融合，三者统一 rawprefix
配置，尚未叠加 reader prompt 修复）也已在三个数据集上全部跑完，详见附录二 B.2/B.3——特征级
融合在多数指标上领先，但仅用全局信号 h 单独已经是比仅用局部信号 Δh 更强的信号，融合相对
h-only 的边际提升小于 h-only 相对 Δh-only 的提升。

一个新观察：**C（仅全局信号 h）三个数据集上在 recall@1/chain@1/EM/F1 上几乎全面超过
