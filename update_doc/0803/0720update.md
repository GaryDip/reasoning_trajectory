# 0720 update — gate_v2 与 h_j probe 的组合探索

承接 [0713update.md](../0713/0713update.md)：那份文档第八节留了一个"下一步"——`adaptive_lambda_rerank`
（学一个逐 hop 自适应权重，替代固定 λ）当时还没有真实结果。这次把这条线走完了，中途踩了三次坑、
最终这个"自适应权重"方向本身被证伪；但过程中顺手把 gate_v2 用 `lr_rerank` 模式重新跑了一遍，
拿到了这个 session 里第一次四项指标同时全面超过 baseline 的结果，并在此基础上把 gate_v2 和 h_j
probe 这两个已经分别验证过的信号真正组合了起来，拿到了目前为止最好的端到端结果。

## 一、K=3/4 数据增强：真实用上了 `train_nl_enhance.jsonl`

`adaptive_lambda_rerank` 训练 λ 模型需要真实候选池数据，复用 `rerank_listwise_contrastive/
build_topk_pools.py` 产出的池子时，发现跟 error_propagation_probe 那次一样的老问题——MuSiQue
本身 K 分布不均衡，train 里 K=2 占大头（61.7%）。用 `data/decompose/musique/gt/
train_nl_enhance.jsonl`（当初为了这个目的准备好、但一直没人用过的 LLM 改写子问题，专门覆盖
K=3/4，`target_k: [3, 4]`）跑了一遍真实 BGE 检索，造出额外的真实候选池（不是复制数据，是换一个
措辞重新检索一遍，天然不同的候选池），补进训练数据：

```
补齐前（原始 pool）：K=2 61.7% / K=3 28.2% / K=4 10.1%
补齐后（59857 个 pool）：K=2 48.0%（28752）/ K=3 38.5%（23013）/ K=4 13.5%（8092）
```

K=3/4 占比明显上来了。这批数据后续用于 `adaptive_lambda_rerank` 的训练。

## 二、`adaptive_lambda_rerank`：自适应权重三次失败，方向本身被证伪

设计思路：不再用固定 λ，训一个很小的模型，输入这一跳的上下文（`q_main_emb`/`h_prev`/
`expanded_q_emb`），输出这一跳专属的 λ，同一个 λ 用在这一跳全部候选上（只决定"这一跳该多信 cosine
还是多信 probe"，不针对具体候选）。loss 是 listwise softmax（gold 排第一），dev 上跟两个固定基线
对比 gold 排名。

### 第一次：无界输出，λ 直接跑飞

`softplus` 激活没有上界，训练发现只要一直调大 λ 就能持续压低 loss，没有任何机制拦着：

```
Dev learned lambda: mean=9.9932  std=2.1244  min=0.0347  max=17.5034
```

| | recall@1 | recall@3 | mrr |
|---|---|---|---|
| 纯 emb_score（λ=0） | 0.8067 | 0.9396 | 0.8778 |
| 固定 λ=0.25（生产默认） | **0.8601** | **0.9635** | **0.9145** |
| 学出来的 λ | 0.701 | 0.877 | 0.8015 |

学出来的还不如纯 cosine，**全面倒退**。

### 第二次：加上界（`lambda_max·sigmoid`），结果卡死不动

给 λ 设了 `[0, 2]` 的硬边界。但训练完全学不动，loss 卡在 ~1.86 反复横跳好几个 epoch 不降。查了
真实数据才发现根因：`h_prev`（Llama 原始隐藏状态）每行 L2 范数均值 ≈149，而 `q_main_emb`/
`expanded_q_emb`（BGE 归一化过）范数是 1.0——尺度差 150 倍，拼进同一个特征向量喂给 MLP，不管最后
用什么激活函数，都会把预激活值推到极端：用无界 softplus 会跑飞（第一次的坑），用有界 sigmoid 会
直接饱和、梯度趋近于零（这一次的坑）——**两次失败是同一个根因，只是换了个症状**。

把 `h_prev` 在过投影层之前做 L2 归一化后，loss 恢复正常下降（8 步内 0.39→0.03，真实数据验证过
梯度健康）。重新跑完整训练，loss 这次能稳步下降到 epoch 23 左右的 0.78（vs 之前卡死的 1.86），
但最终结果是**塌缩成常数**：

```
Dev learned lambda: mean=2.0000  std=0.0000  min=2.0000  max=2.0000
```

模型对所有跳都固定输出上界 2.0，等于变相退化成"固定 λ=2.0"，而且这个值本身就不合理
（recall@1=0.7634，仍然不如固定 0.25 的 0.8601）——listwise loss 的梯度在整个范围内几乎都指向
"λ 越大越好"（因为多扣一点 abnormal_score，大部分情况下确实能把 gold 和非 gold 分得更开），没有
任何"够了别再推"的机制，只要给它空间就会一路顶到上限。

### 第三次：换成有界凸组合 + z-score 校准，训练终于健康，但效果依然不够

把"学一个开放系数"换成"学一个 [0,1] 的混合比例（gate）"：`emb_score` 和 `-abnormal_score` 各自
在池内做 z-score 归一化（消除尺度不一致），再用 `gate·emb_z + (1-gate)·abn_z` 做凸组合——凸组合
的权重加起来必须是 1，结构上就杜绝了"某一方无限压过另一方"。

这次训练终于健康了：

```
Dev learned gate: mean=0.4817  std=0.3788  min=0.0000  max=1.0000
```

gate 有真实方差、覆盖 0~1 整个范围，说明模型真的在按 hop 区分，不再是常数。但最终结果：

| | recall@1 | recall@3 | mrr |
|---|---|---|---|
| 纯 emb_score | 0.8067 | 0.9396 | 0.8778 |
| **固定 λ=0.25** | **0.8601** | **0.9635** | **0.9145** |
| 学出来的 gate | 0.8042 | 0.9318 | 0.8736 |

**依然没有超过固定 0.25，甚至比纯 emb_score 还略差。** 训练过程的三个 bug 全部修完之后，这条路线
本身的天花板还是没打破——根本原因：这个模型的输入全部是**检索发生之前**就定好的文本上下文（主
问题、走到这里的推理状态、当前子问题），它从头到尾**没看过这一跳实际召回出来的候选长什么样**，
单靠预判"这是个什么样的问题"去猜权重，信息量不够。**结论：context-only 的自适应加权这条路线
本身有问题，不是训练没调好——需要能看到实际候选打分的信号，而不是检索前的盲猜。**

### 一个中间验证：RRF（不需要训练）

在放弃"学权重"之前，用不需要训练的 Reciprocal Rank Fusion（倒数排名融合）试了一版，只融合
emb_score 和 h_j-probe 两路（当时还没有 gate_v2 的候选级数据）：

| | recall@1 | recall@3 | mrr |
|---|---|---|---|
| 纯 emb_score | 0.8067 | 0.9396 | 0.8778 |
| 学出来的 gate | 0.8042 | 0.9318 | 0.8736 |
| RRF（k=10） | 0.8304 | 0.9539 | 0.8959 |
| 固定 λ=0.25 | **0.8601** | **0.9635** | **0.9145** |

RRF 比纯 emb_score 和学出来的 gate 都好，但还是没打过固定 λ=0.25——这一版只融合了两路，没有
gate_v2，后面第五节会看到加入 gate_v2 之后 RRF 的表现（依然不如直接加权）。

## 三、gate_v2 换成 `lr_rerank`：第一次四项指标同时全面超过 baseline

0713update.md 第一节验证 gate_v2 时用的是 `gated_rule_a`（二元触发，gate 分数超阈值才扩池，
gate 本身不参与排序）。这次直接用生产脚本 `run_retrieval_exp_wavefront.py --methods lr_rerank`
（连续混合公式 `emb_score - λ·gate_score`，跟 h_j-probe 那边用的是同一种公式结构）重新跑了一遍，
其它参数保持跟之前 `gated_rule_a` 那次一致（`lambda_lr=0.25`、`decompose_mode=bart_decompose`、
`artifacts_dir=gate/artifacts_pooled_v2`）：

| | recall@1 | chain_recall@1 | EM | F1 |
|---|---|---|---|---|
| baseline `gated_rule_a`（31层） | 0.6513 | 0.4233 | 0.4079 | 0.5012 |
| gate_v2 `gated_rule_a`（混层，二元触发） | 0.6565 | 0.4290 | 持平 | 持平 |
| **gate_v2 `lr_rerank`（连续混合）** | **0.6627** | **0.4357** | **0.4100** | **0.5045** |

**这是这个 session 里第一次四项指标同时全面超过 baseline**——之前 gate_v2 的二元触发版本只是
检索指标涨、答案指标持平；这次换成连续混合公式后，四项全涨，虽然每项涨幅不算夸张，但方向一致，
没有此消彼长。说明"连续混合"这个公式结构本身，比 gate_v2 原来的二元触发用法更好，跟 h_j-probe
那边"混合比单独用/单独触发更稳"的经验一致。

## 四、gate_v2 和 h_j-probe 的重叠分析：证明两者互补，值得组合

在决定要不要花力气把两个信号真正组合起来之前，先直接比了一下两边的真实结果，看"谁做对的样例"
重不重合——如果完全重合就没必要合并。用上一节的 gate_v2 `lr_rerank` 结果和之前的 h_j-probe
`weighted`（λ=0.25）结果，按 id 对齐比较（2417 个共同样例）：

**chain_recall1（检索链路）：**
```
两个都对：  911 (37.7%)
两个都错： 1186 (49.1%)
只 gate_v2 对： 142 (5.9%)
只 h_j-probe 对： 178 (7.4%)
```

**答案 EM：**
```
两个都对：  797 (33.0%)
两个都错： 1273 (52.7%)
只 gate_v2 对： 194 (8.0%)
只 h_j-probe 对： 153 (6.3%)
```

两项指标上都有 **13~14%** 的样例是"只有一个方法做对"——不是谁包含谁，是两边各自独立在不同样例
上有效。理想情况下（完美挑对）EM 上限能到 47.3%，比单用任何一个（约 39~41%）都高出不少。
**结论：两个信号不是同一件事的两种说法，值得合并。**

## 五、`combined_gate_rerank`：三种投票方式对比，简单加权求和胜出

新建了 `combined_gate_rerank/wavefront_combined_gate.py`，两个信号在**同一次批量前向传播**里
一起打分（gate_v2 按自己的 j 用 15/23 层，probe 固定 31 层，一次 `batch_last_hidden` 把这几层
都问出来，不需要跑两次 Llama），支持三种投票方式：

| 投票方式 | 公式 | recall@1/oracle | chain 相关 | EM | F1 |
|---|---|---|---|---|---|
| baseline | — | 0.6513 | 0.4233 | 0.4079 | 0.5012 |
| gate_v2 `lr_rerank`（单独） | — | 0.6627 | 0.4357 | 0.4100 | 0.5045 |
| h_j-probe `weighted`（单独） | — | 0.6735 | 0.4659 | 0.393 | 0.4816 |
| **联合 `sum`** | `emb - λ1·gate_v2 - λ2·probe`，λ 各 0.25（复用各自已验证的值） | **0.6869** | **0.4894** | **0.4141** | **0.5089** |
| 联合 `veto` | 任一模型判定异常（p>0.5）就否决，剩下按 cosine 排 | 没有效果 | | | |
| 联合 `rrf` | 两边各自完整重排后，融合**名次**（不是分数） | 0.6705 | 0.4564 | 0.3922 | 0.4822 |

**`sum`（最简单的固定权重求和）是三种里唯一全面超过之前所有单独方法的**，`veto` 和更"精巧"的
`rrf`（不需要做尺度校准，只融合排名先后）反而都不如它——`rrf` 检索侧还行但答案侧甚至不如
baseline，大概率是因为它只看名次、丢掉了"有多确定"这个置信度信息，而 `sum` 保留了原始分数的
幅度差异。这也再次印证了第二节的经验：**越简单直接的固定权重组合，比越"聪明"的方案更稳。**

### 协同作用验证：不是"选更强的那个"，是真的互补

用第四节同样的方法，检查 `sum` 模式相对两个单独方法的"重叠恢复率"：

```
只有 gate_v2 单独对的 142 个样例：联合模型保住了 47.2%
只有 h_j-probe 单独对的 178 个样例：联合模型保住了 78.1%
两个单独都错的 1186 个样例：联合模型新修好了 4.9%（约 58 个）
```

最后一行最关键——这 58 个样例，gate_v2 和 h_j-probe 单独看都是错的，只有两个信号组合起来才做对，
不是"联合模型学会了偏向更准的那个",是真的从组合信息里挖出了单独任何一个都拿不到的正确答案。
前两行也说明协同是双向的——没有偏废任何一方。**结论：确认存在真正的协同效应，不只是均值意义上
的提升。**

## 六、下一步（进行中）：置信度加权

`sum` 模式虽然是目前最好的，但离"理想情况下完美挑对"的 47.3% EM 上限还有明显差距——用固定权重
到处都一样地混，没有针对"这一跳该多信哪个"做任何区分。下一步想法：不训练模型，用两个信号**各自
在这一跳候选池内部的打分标准差**（越分散说明这次判断越果断、越有信息量）算一个动态权重：

```
w_gate  = gate_v2置信度 / (gate_v2置信度 + probe置信度)
w_probe = 1 - w_gate
最终分数 = emb_score - (2×0.25×w_gate)·gate_v2_score - (2×0.25×w_probe)·probe_score
```

两边置信度相近时自动退化成 `sum` 模式（各 0.25），只有某一跳里两边"果断程度"差很多时才真的倾向
更自信的那个——不用训练，不会重演第二节那三次"学出来的权重不可控"的坑。

验证这个不需要重跑端到端：`adaptive_lambda_rerank` 已经有 gate_v2 和 h_j-probe 各自完整候选池
的打分基础设施，只差给现有的 `musique_{train,dev}_lambda_data.npz` 补一列 `cand_gate_v2_score`
（`add_gate_v2_scores.py`，chunked+可续跑，`pool_id` 对齐检查真实跑通：dev 6404 个 pool、train
59857 个 pool 全部按行对齐验证通过）。补完之后全部在 CPU 上离线验证，不用每改一个想法就重跑一次
GPU 端到端。

**这一步实际跑完了，结果如下——三种"更聪明"的变体，没有一个打过最朴素的固定权重求和：**

| 方法（dev，gold rank recall@1） | 数值 |
|---|---|
| **`sum`（固定 0.25/0.25）** | **0.8660** |
| confidence-weighted（按池内打分标准差动态分配权重） | 0.8646 |
| coarse(probe)→fine(gate_v2) k=3 | 0.8643 |
| coarse(probe)→fine(gate_v2) k=5 | 0.8624 |

进一步做了 (λ_gate, λ_probe) 独立网格搜索，整体 recall@1 最优是 (0.25, 0.10) → 0.8690，看起来比
`sum` 还高一点；但按第四/五节同样的"重叠恢复率"口径再看一遍，发现这个配置是牺牲 probe 独有正确
样例的保住率换来的（50.6% vs `sum` 的 72.1%），协同修复率（两个单独都错、组合修好）也从 5.5% 掉到
1.5%——**收回之前"0.25/0.10 更好"的建议**：整体数字涨了，但代价是明显牺牲了两个信号的互补性。

又试了三方凸组合（cosine + probe + gate_v2 权重和为 1，z-score 后组合）：整体 recall@1 最优是
(0.6, 0.2, 0.2) → 0.8679；均等三分 (0.33, 0.33, 0.33) → 0.8463（整体反而更差），但"两个单独都错、
组合修好"的协同修复率高达 **16.0%**（`sum` 是 5.5%）——**再次验证同一个权衡：越偏向"整体准确率
最大化"的权重配置，协同效应越弱；权重越均衡，协同效应越强但整体数字会掉。** 到这里"怎么调权重"这
条路线已经反复验证过很多变体，全部是在同一个权衡曲线上挪动，没有真正跳出"事后组合两个独立模型的
输出分数"这个框架。

## 七、gate v3：特征层面融合，不是事后组合两个分数

前面所有组合方式（`sum`/`veto`/`rrf`/confidence-weighted/coarse-then-fine/三方凸组合）都是**后
融合**——gate_v2 和 h_j-probe 各自独立训练好，推理时把两边的**输出分数**加权/投票/融合排名。
gate v3 换一个思路：**特征层面融合**——同一个 hop 的 Δ_j（gate_v2 的原始特征）和 h_after（probe
的原始特征，累计到当前 hop 为止的整条前缀）各自单独做 PCA（协方差结构不一样，不能共用一个 PCA），
把两组降维后的特征拼接成一个向量，只训练**一个** LogisticRegression，让模型自己去学这两种信息该
怎么组合，而不是训练完两个模型后再手工调权重。

复用 gate_v2 已经验证过的层选择（j=0/1 用第 15 层，j=2/3 用第 23 层——v3 没有重新搜层，两个特征
同一个 j 共用同一层的输出），复用已经提取好的 `hidden_states/pilot_multilayer/`，**不需要新的
GPU 提取工作**，纯 CPU 训练：

```
j=0 Q->E1   K=[2,3,4] n=83927 pos=28.7% train_auc=0.9707
j=1 E1->E2  K=[2,3,4] n=59857 pos=40.2% train_auc=0.9472
j=2 E2->E3  K=[3,4]   n=21411 pos=45.3% train_auc=0.9143
j=3 E3->E4  K=[4]     n=4046  pos=50.0% train_auc=0.9535
```

dev 上直接跟 gate_v2（Δ only）的原生指标（不经过端到端，AUC/F1 这类"该不该触发干预"的分类指标）
对比：

| | AUC | overall F1 | overall TPR | j=1 F1 | j=2 F1 |
|---|---|---|---|---|---|
| gate_v2（Δ only） | 0.9221 | 0.7785 | 0.8456 | 0.776 | 0.7535 |
| **gate v3（h_after ⊕ Δ）** | **0.9357** | **0.793** | **0.8838** | **0.806** | **0.7919** |

**这是这个 session 里第一次有组合方案在 gate 自己的原生离线指标上干净利落地全面超过 gate_v2**——
之前所有后融合的变体都是在下游端到端指标上打转，没有一个从根子上（gate 自身的判断准确率）超过
gate_v2。j=2（E2→E3，gate_v2 本来最弱的一跳）F1 涨幅最大（+0.038），符合直觉：这一跳信息量最难判
断，加上"整条前缀走到这里是什么状态"这个全局信号后，判断力提升最明显。

（训练时踩了一个环境坑：第一次训练用的 conda `base` 环境 sklearn 是 1.8.0，而实际打分用的
`mlsys` 环境是 1.7.2——1.8.0 之后 `LogisticRegression` 不再存 `multi_class` 这个实例属性，
1.7.2 的 `predict_proba` 还依赖它，直接导致跑端到端时 `AttributeError`。用 `mlsys` 重新训练一遍
后问题消失，dev 指标数值不变，纯粹是环境不一致导致的序列化兼容性问题，不影响上面的结论。）

## 八、gate v3 端到端验证：离线的赢，真的兑现成端到端的赢了

production 的打分入口 `score_gate_requests` 是按"单个 PCA + 单个 LR 作用在 Δ 上"这个约定硬编码
的，读不了 v3 这种双 PCA 拼接的 artifact，所以新写了一个脚本
`retrieval/run_retrieval_exp_wavefront_gate_v3.py`（大量 import 复用
`run_retrieval_exp.py`/`run_retrieval_exp_wavefront.py` 的数据加载、批量 hidden state 提取、
vLLM 生成、accumulator 这些，两个生产文件本身一行没改），单跳打分公式跟 gate_v2 的 `lr_rerank`
完全一样（`emb_score - λ·gate_score`，λ=0.25），唯一区别是 `gate_score` 换成了 v3 的
`lr.predict_proba(concat(pca_h.transform(h_after), pca_delta.transform(Δ_j)))`。beam_width=1，
跟 gate_v2 `lr_rerank` 那次同参数、同一份全量 musique dev（2417 条）：

| | recall@1（hop_match） | chain_match | EM | F1 |
|---|---|---|---|---|
| baseline（`gated_rule_a`，31 层） | 0.6513 | 0.4233 | 0.4079 | 0.5012 |
| gate_v2 `lr_rerank`（Δ only） | 0.6627 | 0.4357 | 0.4100 | 0.5045 |
| **gate v3（h_after ⊕ Δ）** | **0.6950** | **0.5010** | **0.4224** | **0.5146** |

四项全赢，且赢的幅度是这个 session 里最大的一次：hop_match +3.2 个点，chain_match **+6.5 个点**
（涨得最猛），EM +1.2 个点，F1 +1.0 个点。chain_match 涨幅明显大于 hop_match，跟第七节里"j=2 这个
最弱环节改善最多"的离线结果对得上——链路越长，单跳的弱点被放大得越明显，修好最弱的一跳对整条链路
正确率的杠杆最大。

**这是这个 session 里第一次"离线指标赢"真正兑现成"端到端也明显赢"的结果。** 前面第五、六节所有
后融合的组合方式，端到端都没能稳定超过 gate_v2 单独的 `lr_rerank`；v3 用特征层面融合，一次训练
就干净利落地全指标胜出——说明"两个信号该怎么组合"这个问题，与其在**已经独立训练好的两个模型的
输出分数**上继续调权重，不如让模型在**原始特征**层面自己学怎么组合，信息损失更少。

**下一步（还没试）**：v3 目前 h_after 和 Δ 共用 gate_v2 已经验证过的同一层（j=0/1→15 层，
j=2/3→23 层），没有分别给 h_after 和 Δ 单独调过层——如果后面还想再往上抠一点，这是一个可以试的
方向。

## 九、context gate：学出来的"逐候选"组合权重——离线赢了，端到端跟 v3 打平

v3 是"特征层面融合成一个模型"，跟它平行的另一条路是"两个已经练好的模型（gate_v2 + probe）继续
分开用，但学一个更聪明的组合方式，取代 sum 的固定 0.25/0.25"。第五、六节试过的所有"更聪明"的组合
（confidence-weighted、coarse-then-fine、网格搜索、三方凸组合）都只是**一跳一个权重**，跟老
`adaptive_lambda_rerank` 犯的错误是同一类——权重是"检索前"或者"整跳级别"定下来的，同一跳里所有
候选共用一份。这次换了个新提案：**权重精细到每一个候选**。

### 提案：α 由每个候选自己的 h_after 决定，不是一跳共用一个

```
alpha_i   = sigmoid(w^T h_after_i + b)              -- 每个候选各自算,不是一跳一个
anomaly_i = alpha_i * gate_v2_score_i + (1-alpha_i) * probe_score_i
final_i   = emb_score_i - 0.5 * anomaly_i           -- 0.5 = sum 公式本来的 0.25+0.25 总预算
```

跟老 adaptive_lambda 的本质区别：老版本的输入（`q_main_emb`/`h_prev`/`expanded_q_emb`）是检索前
就定好的、一跳所有候选共用同一份，训练时模型看不到"具体选了哪个候选"，梯度只能笼统地说"这一跳整体
该偏局部还是偏全局"，没有候选级别的差异化信号，这是它反复崩溃（跑飞/卡死/塌缩成常数）的根因。新
提案的 α 由**这个候选自己选中之后的 h_after** 决定，同一跳里不同候选可以算出不同的 α——训练时第一次
有了真实的"因候选而异"的梯度信号。

### 数据：复用现成的，只多补一列

`adaptive_lambda_rerank` 的候选池数据（`cand_emb_score`/`cand_gate_v2_score`/`cand_abnormal_score`）
已经现成，只缺"每个候选自己的 h_after 向量"这一项。写了 `add_probe_h_vector.py`（跟
`add_gate_v2_scores.py` 同样的 chunked+可续跑+pool_id 对齐校验模式），补了一列 `cand_h_pca`
(probe 自己 PCA 压缩后的 64 维向量，复用 probe 已有的层(31)和 PCA，不是新算的东西)：

```

train: (1197068, 64) 无 NaN/Inf
```

### 训练结果（新目录 `context_gate_rerank/`）：离线 gold-rank 上，第一次"整体 + 协同"同时双赢

模型极简（65 个参数：一个 `Linear(64,1)` + sigmoid），在 `adaptive_lambda_rerank` 的 dev 候选池
（6404 个）上离线验证：

| | recall@1 | 两个单独都错时,修好的比例(协同) |
|---|---|---|
| gate_v2 单独(0.25) | 0.862 | — |
| probe 单独(0.25) | 0.8601 | — |
| sum(固定 0.25/0.25，之前最好) | 0.866 | 5.5% |
| **learned context gate** | **0.8776** | **16.4%（约 3 倍）** |

α 的分布健康（mean=0.5593, std=0.4636, 覆盖 0~1 全范围），不是塌缩成常数。**这是这个 session 里
第一次"整体准确率"和"协同修复率"同时双赢**——之前三方凸组合那次必须二选一（整体好 vs 协同好），
这次不用取舍了。唯一的不对称：保住 gate_v2 独有正确样例的能力（81.5%）比 `sum`（57.1%）强很多，
但保住 probe 独有正确样例的能力（59.3%）反而比 `sum`（72.1%）略弱——大概率是训出来的 α 均值略偏向
本来就更强的 gate_v2，不是 bug。

### 端到端验证：检索侧确实更好，但答案侧没跟上

新建 `context_gate_rerank/wavefront_context_gate.py`（跟 `combined_gate_rerank` 同样的结构，共享
一次批量前向传播，换成加载训练好的 gate 网络算 α），跑了一次全量 musique dev：

| | recall@1 | chain | EM | F1 |
|---|---|---|---|---|
| gate v3 | 0.6950 | 0.5010 | **0.4224** | 0.5146 |
| **context gate** | **0.7018** | **0.5184** | 0.4208 | **0.5147** |

检索侧（recall@1、chain）确实比 v3 更好，chain 涨了 1.74 个点，是目前所有方案里最高的；但答案侧
（EM、F1）基本打平，EM 甚至略低 0.16 个点（噪声范围内）。说明离线候选池排序上的优势，这次**没有
完全兑现成答案侧的提升**——大概率是 reader 本身的瓶颈（EM 是严格字符串匹配），不代表检索侧的提升
是假的，但也不是 v3 那种"四项指标同步全面碾压"的干净胜出。

### 结论：效果打平，选 v3 作为默认

两个方案端到端效果基本打平（各有侧重，不是谁碾压谁），但 v3 结构更简单——一个 LR，复用 v2 已验证
的层选择，sklearn 一次训练完事；context gate 是 gate_v2 + probe + 额外训练一个 PyTorch 门控网络，
三个组件拼起来，链路更长（训练时还真的因为 sklearn 版本不一致炸过一次）。**效果差不多时，选活动
部件更少的方案**——v3 定为默认方案，context gate 作为已验证过、检索侧略有优势的备用选项留着，不
继续投入。
